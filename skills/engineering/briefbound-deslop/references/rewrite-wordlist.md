# 改写词表与场景细则

本文件是 briefbound-deslop 的扩展细则：黑话两档词表、生硬词替换、场景细则与微例。改写时按需取用，不必整体加载。

## 黑话词表

绝对禁用（必须换成具体动作，或整句删除）：

- 赋能、抓手、闭环、沉淀、拉通、链路、兜底、洞察（作空名词时）
- 扩展同档：发力、深耕、打法、组合拳、顶层设计、底层逻辑、护城河（非商业分析语境）、势能、心智力

替换原则：问「这句话对应什么具体动作」，写出动作本身。语义对不上原文时不要硬替，回头核对原文或问用户。

谨慎档（上下文确有所指才留，泛指则改）：

- 场景（说清是什么场合）、生态（说清是谁和谁）、布局（说清排了什么）、颗粒度（改「粒度」或「细节」）、复盘（有明确回顾动作才用）、梳理（改「整理/清点」）、对齐（作「沟通确认」解时改具体说法）

技术名词豁免：架构意义上的 base/底座、数据库的链路追踪、闭环控制等术语本义不改。

## 生硬词替换

- 「进行+动词」：进行验证→验证；进行分析→分析。
- 程度副词：非常/十分/极其→很，多数情况直接删。
- 「例如/譬如」→「比如」；「因此/所以」连续出现时删到一处。
- 「实现了对 X 的支持」→「支持 X」；「对 X 进行了优化」→「优化了 X」。
- 滥用被动（「被广泛认为」「被用于」）→ 主动句，主语写清楚。
- 「本方案/本设计/本实施例」在非公文语境少用，直接说「这个方案」。

## 场景细则

技术文档：无问候无寒暄；不堆形容词；先说它是什么、做什么、去哪看更多；步骤编号可扫读；第二人称少用，改祈使句或无人称陈述。

博客：工程师对工程师；少量「你」可用；保留个人判断与取舍的痕迹；开头别复述标题，直接从最有信息量处入题。

发行说明：Breaking → Features → Fixes 分组；一条变更一句；不加 emoji；跟随项目既有措辞风格。

论文与学术：用「我们」陈述工作；数字给具体值，结论挂出处；固定结构（摘要-引言-方法-实验-结论）是文体要求不动；删「结果表明」类的空洞因果，改成具体结论。

推文与社媒：保留个性；社群锚点在前，亮点两三条；感叹号可用但克制；邀请互动优于口号式 CTA。

周报与汇报：只写进展、风险、下一步；删「在…的指导下」类套话；数字与承诺原样保留。

## 微例（改前 → 改后）

- 「性能瓶颈已经不是 I/O，而是锁竞争。」→「瓶颈在锁竞争，不在 I/O。」
- 「通过以上分析，我们可以看出，缓存策略的选择至关重要。」→ 删总结句，只留事实句。
- 「该方案赋能业务快速闭环。」→ 按真实语义改，如「该方案让业务一次提交就能完成审核」；语义不明就问。
- 「随着大模型的快速发展，AI 编程工具如雨后春笋般涌现。」→「过去一年，AI 编程工具多了起来。」
